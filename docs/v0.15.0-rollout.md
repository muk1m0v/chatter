# SALOM 0.15.0 Real-Time — staged rollout notes

This is a preparation document. It does not authorize production changes.

## WebSocket proxy prerequisite

The live Nginx configuration currently routes `/salom/api/` to `127.0.0.1:18731/` and strips the `/salom/api/` prefix. The location does not set HTTP/1.1 upgrade headers and has a 12-second read timeout, so the Android WebSocket cannot stay connected through this proxy. Before enabling the client, add an exact WebSocket location in the existing TLS server block:

```nginx
location = /salom/api/ws {
    proxy_pass http://127.0.0.1:18731/ws;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 75s;
    proxy_send_timeout 75s;
    proxy_buffering off;
    add_header Cache-Control no-store;
}
```

Validate with `nginx -t`, then schedule a reload separately. The current configuration must remain in place until an approved rollout.

## Current implementation state

- WebSocket authentication uses the existing bearer token in the `Authorization` header; the token is not placed in the URL.
- The process-local hub caps at 24 total sockets and 5 per account, subscribes a socket to one peer, rate-limits typing events, forwards messages, typing, presence, and sync invalidations, and filters events by the subscription. The cap leaves headroom under the current Uvicorn concurrency limit of 32; raise both only after load measurements.
- Message and typing events are published only after the database context commits. HTTP message history remains the reconnect/fallback synchronization path.
- The Android conversation opens a foreground socket, reconnects with exponential backoff, and waits for an acknowledged subscription before disabling frequent HTTP history, typing, and presence polling.
- The hub is process-local and is safe only with the current single Uvicorn worker. Redis Pub/Sub is required before increasing worker count.

## Read-only VPS snapshot (2026-11-16)

- `salom-api.service` was active with zero recorded restarts. Its Uvicorn process had 1,024 open descriptors: 507 references to `directory.sqlite3`, 505 to its WAL, one to the shared-memory file, and nine sockets. This confirms leaked SQLite handles as the immediate cause of the descriptor exhaustion. The repository now explicitly closes every SQLite connection in `connect()`; the deployed process is still running the old code, so this correction needs a controlled deployment/restart.
- The process soft descriptor limit was 1,024 and hard limit 524,288 even though systemd reports a 524,288 limit. The local service unit now requests `LimitNOFILE=8192:524288`; validate the effective soft and hard values after the approved deployment.
- At the initial snapshot RSS was about 252 MiB against `MemoryMax=256M`. A later read-only snapshot showed cgroup memory at 268,308,480 / 268,435,456 bytes, 1,024 descriptors still open, 370 `max` events, no OOM kills, and 53,294 journal lines containing `Errno 24` since midnight. This is an immediate operational risk; increasing the fd limit alone would defer rather than fix it. No sustained CPU or memory trend has been measured.
- PostgreSQL and Redis listen only on loopback. Nginx listens on ports 80/443. The API listens on loopback port 18731. `nginx -t` passes, but the live SALOM proxy has no WebSocket upgrade headers and a 12-second read timeout.
- SQLite permissions were `0600` under a `0700` data directory; attachments were under a `0700` directory. Firebase admin credentials were `0640 root:salom-api` under a `0750 root:salom-api` directory. UFW was active with SSH and Nginx ports open from any source. SSH password and keyboard-interactive auth were disabled, while root key login remained enabled.
- The served TLS certificate was valid until 2027-01-28. Local SQLite/media backup files and backup timers exist under `/var/backups`, but they are on the same VPS; off-site encryption and restore have not been verified.

## Remaining release gates

- `backend/deploy.py` is now a read-only source preflight. The prior helper could restart production while omitting the new database/WebSocket modules and dependencies; do not use the old deployment sequence.
- Install and validate the Nginx WebSocket location in a controlled staging environment.
- Exercise WebSocket behavior end-to-end through Nginx, including network loss, receipts, edits, deletes, and background push behavior.
- Room caches remote messages and conversations and now has a durable outgoing queue with stable `client_id` retries. The migration rehearsal passed with synthetic rows in an isolated PostgreSQL database, and one API smoke test covers messages, attachments and locations; this is not a production-data migration rehearsal. Device-level offline/restart behavior still needs validation. Production still uses SQLite.
- Run isolated 25/50/100-client load tests and record p50/p95 delivery latency and resource use.
- Verify the existing release signing key. The Gradle release task now fails closed instead of using the debug key; no existing keystore was found in the worktree, so a distributable upgrade APK is not ready. See [release signing setup](release-signing.md).
- Back up production SQLite/media and rehearse restore before any database cutover.
