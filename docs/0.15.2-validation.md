## Call limitations requiring device validation

The duplicate ringtone cause is confirmed in code: the notification channel and Conversation each played the ringtone. Conversation playback was removed; notification owns the alert. Acceptance cancels it before network negotiation.

The exact reported Android crash has not been reproduced or captured in logcat. Foreground service runtime failures are now logged instead of escaping on the main service thread. This does not establish that every device call failure is resolved.

CallSessionManager gates Call IDs and repeated acceptance, but the full WebRTC engine is still owned by the conversation. Activity recreation and background call continuity require further verification. No connected physical Android device was available; the configured emulator cannot start without hardware acceleration.

Manual device checks: Windows to locked Android, open app while ringing, accept repeatedly, reject, end, rotate the screen, background the app, reconnect the network. Capture logcat and exit history using tools/capture-call-crash.ps1 if a failure occurs. Do not describe real Android/Windows calls as verified until these checks pass.
